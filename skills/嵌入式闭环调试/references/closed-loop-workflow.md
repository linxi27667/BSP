# 闭环调试流程

## 闭环定义

闭环不是“给建议”，而是持续执行：

1. 观察：收集代码、配置、原理图、日志、端口、下载器状态。
2. 假设：根据证据提出一个最可能根因。
3. 修改：做最小改动或增加最小观测点。
4. 验证：编译、烧录、运行、采集日志。
5. 对比：确认新证据是否支持假设。
6. 迭代：成功则收尾，失败则建立下一假设。

## 每轮记录模板

```text
目标:
本轮假设:
改动:
构建结果:
烧录/下载结果:
运行证据:
结论:
下一步:
```

## 决策顺序

1. 构建失败优先于运行问题。
2. 烧录/连接失败优先于固件逻辑问题。
3. 复位/崩溃优先于功能细节。
4. 内存/栈/看门狗优先于 UI 美观。
5. 协议链路先验证“收得到”，再验证“解析对”，最后验证“业务状态对”。

## 何时询问用户

- 需要选择真实 COM 口、下载器、目标板型号。
- 需要用户手动按 BOOT/RESET、插拔 USB、关闭占用串口的软件。
- 需要执行擦全片、改量产配置、改 fuses/option bytes 等不可逆动作。
- 需要确认硬件连接、电源、拨码、跳线。

## 不要做的事

- 不要在没有证据时大规模重构。
- 不要把编译通过当作运行成功。
- 不要只截取最后几行日志，嵌入式问题经常根因在启动早期。
- 不要忽略用户已经打开的串口工具、Keil 工程配置、Trae/IDE 状态。
- 不要把 GUI 工具的弹窗当成失败结束；应说明需要用户交互或切换 CLI 工具。
